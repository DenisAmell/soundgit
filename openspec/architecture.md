# SoundGit — архитектура

> Целевая архитектура. Что уже построено — в `openspec/specs/`, что строится — в `openspec/changes/`.
> **[решение]** — выбор, сделанный при проектировании; рядом указана причина и отвергнутая альтернатива.

## 1. Компоненты

### Границы ответственности

| Компонент | Отвечает за | Не делает |
|---|---|---|
| Ядро (Go) | Парсинг, IR, diff, merge, хранилище, синхронизация, lock плагинов | UI |
| Клиент (C++/JUCE) | Отображение истории, diff, конфликтов; команды ядру; сообщает агенту состояние транспорта | Парсинг проекта, сеть до сервера, работа в аудиопотоке |
| Мост (ReaScript) | Сохранить проект, перезагрузить проект, сообщить «есть несохранённые правки» | Логика версий |
| Сервер (NestJS) | Аутентификация, права, хранение объектов и ссылок, атомарное обновление веток, блокировки | Слияние (оно всегда на клиенте) |
| Research (Python) | Слияние сигналов, эмбеддинги, описание изменений LLM, эксперименты | Не входит в критический путь продукта |

### Ключевые решения

- **[решение] Вся логика версий — в одном Go-бинарнике, клиент тонкий.** Причина: требование «не грузить проект» и офлайн-режим; один бинарник тривиально собирается под три ОС; CLI даёт тестируемость без DAW и UI. Альтернатива «логика в JUCE-плагине на C++» отвергнута: плагин живёт в процессе DAW, падение или блокировка ломает сессию; плагин всё равно не видит проект хоста.
- **[решение] Интеграция с DAW — через файл проекта.** Причина: единственный способ, общий для всех DAW. Альтернатива «нативное расширение Reaper на C++ с доступом к API» даёт живое применение без перезагрузки, но привязывает к одной DAW; оставлена как возможное развитие моста.
- **[решение] Слияние на клиенте, сервер «глупый».** Причина: офлайн-режим, конфиденциальность, простота сервера; сервер только проверяет, что обновление ветки — fast-forward.
- **Audio Backuper — отдельный мини-продукт** (решение автора, 2026-11-15): свой плагин, своё окно, своя фоновая часть. Он не переносится в агент SoundGit и не удаляется. Описание и разбор прототипа — в [audio-backuper.md](audio-backuper.md).
- **Стек (из НИР, зафиксирован):** C++/JUCE — клиент; Go — ядро/агент; Node.js/NestJS — сервер; PostgreSQL; S3/MinIO; Docker; Python/PyTorch — исследования.

## 2. Адаптер Reaper и IR

### 2.1. Два слоя: дерево без потерь и семантическая модель **[решение]**

`.rpp` — текстовое дерево блоков `<TAG аргументы … >` со строками-атрибутами. IR не может покрыть все поля Reaper, а терять непонятые поля нельзя (анти-цель). Поэтому:

1. **Дерево RPP** — парсер читает файл в обобщённое дерево узлов (тег, токены, дочерние узлы, сырые строки для base64-блоков). Запись дерева обратно даёт **побайтово исходный файл**.
2. **IR** — типизированная проекция дерева. Каждая сущность IR хранит известные поля типизированно, а всё остальное — в `ext.reaper` как непрозрачные именованные фрагменты, привязанные к сущности-владельцу.
3. **Писатель** собирает `.rpp` из IR: известные поля сериализует сам, `ext` вставляет как есть.

Слияние работает над IR: известные поля — по типам, непрозрачные фрагменты — трёхсторонне «по ключу целиком».

### 2.2. Идентичность сущностей

Слияние по смыслу требует устойчивых идентификаторов. Reaper их даёт: `TRACKID` (дорожка), `IGUID` (элемент), `GUID` (тейк), `FXID` (эффект), `EGUID` (огибающая). Они становятся ID сущностей IR. У точек автоматизации, MIDI-нот и точек темпа ID нет — для них используется слияние по интервалам времени (§4).

### 2.3. Модель IR (черновик)

```
Project
  meta        { sampleRate, daw, dawVersion, irVersion }
  tempoMap    [ TempoPoint { time, bpm, timeSigNum, timeSigDen, shape } ]
  markers     [ Marker { id, time, end?, name, color } ]
  trackOrder  [ TrackId ]
  tracks      { TrackId → Track }
  ext

Track
  id, name, color
  volume, pan, mute, solo, phase
  folderDepth                       // иерархия папок
  receives    [ Receive { srcTrackId, volume, pan, mode } ]   // посыл хранится на принимающей дорожке
  fxOrder     [ FxId ]
  fx          { FxId → Fx }
  envelopes   { EnvelopeId → Envelope }
  items       { ItemId → Item }
  ext

Fx        { id, format (VST3/VST2/AU/JS/CLAP), ident, name, bypass, offline, stateHash, envelopes, ext }
Envelope  { id, target (volume/pan/mute/width/tempo/param:<id>…), active, points [ { time, value, shape } ], ext }
Item      { id, position, length, fadeIn, fadeOut, mute, loop, activeTake, takes [Take], ext }
Take      { id, name, offset, playrate, pitch, source: AudioSource | MidiSource, ext }
AudioSource { assetPath (относительный, POSIX), assetHash }
MidiSource  { ppq, events [ { tick, type, channel, data } ] }
```

Нормализация: время — секунды с фиксированной точностью; числа — каноническая запись; пути — относительные к корню проекта, разделитель `/`, Unicode NFC; состояние плагина (`stateHash`) — хеш декодированного блока, сам блок лежит отдельным объектом.

### 2.4. Независимость от DAW

Ядро IR не содержит понятий Reaper; специфика — только в `ext.<daw>`. Адаптер DAW реализует интерфейс `Parse(файл) → IR` и `Write(IR) → файл`. Diff, merge, хранилище, синхронизация про DAW не знают. Проверка тезиса — адаптер Ableton `.als` (gzip + XML) на этапе 8.

### 2.5. Уровни поддержки DAW

Не каждый формат позволяет чтение и запись. Адаптер объявляет уровень, ядро включает функции по нему:

| Уровень | Требует от адаптера | Даёт пользователю | DAW |
|---|---|---|---|
| 1. Пакет | Перечислить файлы проекта и что игнорировать | История, откат, синхронизация, дедупликация аудио, обнаружение параллельных правок | любая |
| 2. Чтение | `Parse → IR` (возможно, частичный) | Сравнение версий по смыслу | Logic Pro (частично) |
| 3. Чтение и запись | `Parse` и `Write` без потерь | Автоматическое слияние | Reaper, Ableton Live |

**[решение] Первая DAW — Reaper, уровень 3** (подтверждено автором 2026-11-15 после рассмотрения Logic Pro). Причина: главный результат диссертации — семантическое слияние — достижим только на уровне 3.

**Logic Pro — исследовано, отложено (этап 9, уровень 1 с элементами 2).** Проект `.logicx` — пакет: `Alternatives/NNN/ProjectData` (закрытый бинарный формат Apple без документации; дорожки, регионы, MIDI, микшер, плагины, автоматизация), `Alternatives/NNN/MetaData.plist` (читается: темп, тональность, размер, частота дискретизации, число дорожек, списки аудиофайлов и сэмплерных инструментов), `Resources/ProjectInformation.plist` (версия Logic, имена альтернатив), `Media/`. Сообщество разобрало `ProjectData` частично и только на чтение (оценка ~60%: имена дорожек и регионов, список плагинов; MIDI, микшер и кривые автоматизации не расшифрованы); формат меняется между версиями Logic. Поддержки DAWproject нет; AAF теряет плагины и инструменты. Следствия для будущего адаптера:
- слияние `ProjectData` невозможно → при параллельных правках аудиофайлы объединяются, а чужая версия проекта материализуется как «Альтернатива» в том же пакете, и пользователь переносит дорожки штатным импортом Logic;
- из версии исключаются служебные данные пакета: `Undo Data.nosync`, `Project File Backups`, `WindowImage.jpg`, состояние окон;
- Logic работает только на macOS.

## 3. Объектная модель хранилища

Всё неизменяемо и адресуется хешем BLAKE3 содержимого (как в Git).

| Объект | Содержимое |
|---|---|
| `chunk` | Блок байтов ассета (FastCDC) |
| `asset` | Манифест: размер, формат, упорядоченный список хешей чанков |
| `blob` | Непрозрачные данные: состояние плагина, крупные `ext`-фрагменты |
| `track` | Каноническая сериализация одной дорожки IR |
| `snapshot` | Проект: meta, tempo, markers, огибающие проекта, trackOrder, `{TrackId → хеш track}`, `{путь → ассет}`, исходный файл проекта (`blob`); позже — хеш lock-файла плагинов |
| `commit` | Хеш snapshot, родители, автор, время, сообщение |
| ссылки | `refs/heads/<ветка>`, `HEAD` — изменяемые указатели на коммиты |

- **[решение] Дорожка — отдельный объект.** Неизменённые дорожки между версиями дают тот же хеш: дёшево хранить, быстро сравнивать.
- **[решение] Сериализация — канонический JSON** (отсортированные ключи, нормализованные числа). Причина: отлаживаемость для прототипа и диссертации. Альтернатива protobuf — компактнее, но не читается глазами; можно заменить позже, формат версионирован (`irVersion`).
- **Локальный репозиторий:** каталог `.soundgit/` в корне проекта (`objects/`, `refs/`, `HEAD`, `config`, `safety/`, `index`, `tmp/`).
- **[решение] Снимок хранит и модель, и исходный файл проекта.** Восстановление версии — побайтовое и не зависит от полноты адаптера; модель нужна для сравнения и слияния.
- **[решение] Состояние редактора** (курсор, масштаб, выделение, окна) хранится, но не считается изменением проекта: не показывается в сравнении и не даст конфликтов при слиянии.
- **Параметры FastCDC** (min/avg/max размер чанка) — предмет эксперимента ВКР; стартовое значение avg = 256 КиБ **[решение]**, вынесено в конфигурацию репозитория.

## 4. Diff и трёхстороннее слияние

Вход: base (общий предок), ours, theirs — три IR. Выход: слитый IR + список конфликтов.

| Что сливается | Правило | Конфликт |
|---|---|---|
| Скалярное поле сущности | Изменила одна сторона — берём её; обе одинаково — берём | Обе изменили по-разному |
| Множество сущностей по ID (дорожки, элементы, FX, огибающие) | Добавления объединяются; удаление одной стороной применяется, если другая сущность не трогала | Удалил / изменил |
| Упорядоченный список (порядок дорожек, цепочка FX) | Слияние порядка по ID относительно base | Обе стороны переместили один и тот же элемент в разные места |
| Последовательность без ID (точки огибающей, темп-карта, MIDI-события) | Для каждой стороны вычисляются изменённые интервалы времени; непересекающиеся интервалы применяются оба | Интервалы пересекаются |
| Непрозрачное состояние (состояние плагина, `ext`-фрагмент) | Атомарно: изменила одна сторона — берём | Обе изменили |
| Ассет (аудиофайл) | Атомарно по хешу | Обе стороны заменили содержимое одного пути по-разному |

После слияния — **семантическая валидация**: посылы на удалённые дорожки, элементы со ссылкой на отсутствующий ассет, нарушенная вложенность папок. Нарушения оформляются как конфликты, а не «чинятся» молча.

**Разрешение конфликта.** Конфликт — структура `{сущность, поле, base, ours, theirs}`. Варианты: взять своё, взять чужое, вернуть base. **[решение]** Для элементов и дорожек добавляется «оставить оба»: чужой вариант материализуется как приглушённая дорожка-дубликат «<имя> (theirs)», чтобы сравнить на слух в самой DAW — это естественнее для музыканта, чем текстовый выбор.

**Исследовательское расширение (трек R).** Критерий конфликта для аудио по пересечению носителей правок в плоскости время × частота и слияние сигналов через гомоморфное отображение Φ. В продукт подключается как необязательная стратегия разрешения конфликта ассетов.

## 5. Рабочий каталог, фиксация и откат

- **Фиксация (commit)** — явное действие пользователя: прочитать сохранённый `.rpp`, построить IR, разрезать новые/изменённые ассеты, записать объекты. **[решение]** Автоснимки при сохранении — локальные, не уходят на сервер (этап 5).
- **Внешние файлы.** Ассет вне каталога проекта при фиксации копируется в `media/` проекта, ссылка переписывается на относительную **[решение]**: иначе проект не воспроизводим на другой машине.
- **Восстановление (restore/checkout).** Записывает `.rpp` и материализует ассеты из чанков. Перед любой перезаписью несохранённого в истории состояния создаётся **страховочный снимок** — инвариант «нет потери данных».
- **Откат** — новый коммит с состоянием старой версии **[решение]**; история не переписывается, откат сам откатываем.
- **Применение в DAW.** Этапы 1–4: пользователь переоткрывает проект. Этап 5: мост делает это по команде агента и предупреждает о несохранённых правках.

## 6. Синхронизация

Модель Git: `push` / `pull` поверх HTTPS.

1. Клиент и сервер сравнивают граф коммитов (что есть / чего не хватает).
2. Клиент спрашивает пакетно «каких хешей у вас нет» и грузит только отсутствующие чанки **напрямую в S3** по presigned-URL; сервер байты аудио не проксирует.
3. Ссылка на ветку обновляется атомарно (compare-and-swap); не fast-forward — отказ, клиент делает pull + merge локально.
4. **[решение] Ленивое получение аудио:** pull тянет метаданные всегда, чанки — при восстановлении версии; локальный кэш чистится сборщиком мусора.
5. Блокировки ассетов (этап 6): рекомендательные, на сервере, для файлов, которые нельзя слить.

Аутентификация: OAuth 2.0 / JWT; токен на клиенте хранится в системном хранилище секретов (Keychain / Credential Manager / Secret Service), не в открытом файле.

## 7. Нагрузка на DAW

- `processBlock` клиента пуст; в аудиопотоке нет выделений памяти, блокировок, ввода-вывода.
- Агент — отдельный процесс с пониженным приоритетом; хеширование и сеть ограничиваются по скорости.
- Клиент сообщает агенту состояние транспорта (запись/воспроизведение) — во время записи агент откладывает тяжёлые операции.
- UI клиента опрашивает агента из фонового потока, не из потока сообщений.

## 8. Локальный API агента

HTTP + JSON на `127.0.0.1`, события — Server-Sent Events. Обязательны: случайный токен сессии в заголовке (файл с правами только владельца), отказ запросам с заголовком `Origin` от браузера. Образец — локальный интерфейс помощника Audio Backuper (`core/internal/backuper/helper`): случайный порт, секрет в файле владельца, отказ запросам с `Origin` и чужим `Host`.

## 9. Lock-файл плагинов

`soundgit.lock` строится из цепочек FX снимка: формат, UID плагина, имя, производитель, версия (из локального скана), тип (свободный / коммерческий), ссылка в реестр. При восстановлении версии ядро сверяет установленные плагины и сообщает о недостающих. Установка свободных плагинов из реестра — этап 6; для коммерческих — только манифест-ссылка.

## 11. Мультиплатформенность

| Аспект | Подход |
|---|---|
| Ядро | Go, кросс-компиляция: macOS arm64/x64, Windows x64, Linux x64 |

## 12. Открытые вопросы

- ~~Устойчивы ли GUID Reaper?~~ Проверено на Reaper 7.86: переименование, перемещение и «Save as» их сохраняют; дубликат получает новые; вставка в другой проект сохраняет идентификаторы дорожки и эффектов, но не огибающих. Подробности — в design.md изменения `add-local-versioning-core`.
- **Время в долях или в секундах?** Reaper хранит позиции в секундах и при смене темпа сдвигает все элементы и точки огибающих. Для слияния (этап 3) позиции нужно приводить к долям, иначе смена темпа конфликтует с любой правкой аранжировки.
- **Шум пересохранения.** Reaper при открытии и сохранении дописывает строки и пересохраняет состояние VST. Нужна политика: что считать изменением плагина.
- Параметры плагинов: сливать состояние атомарно или разбирать параметры по отдельности (требует загрузки плагина — вне ядра)? Пока атомарно.
- Идентичность огибающей: `EGUID` или «владелец + цель»?
- Нужна ли модель ветвления пользователю-музыканту или достаточно «моя версия / общая версия»? Влияет только на UI.
