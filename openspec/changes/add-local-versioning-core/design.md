## Context

Первый этап roadmap.md. Общая архитектура — в `openspec/architecture.md` (§2 IR, §3 объектная модель, §5 рабочий каталог); здесь — только то, что нужно для реализации этапа, и решения, уточняющие архитектуру.

Формат `.rpp`: текстовый файл, дерево блоков. Блок открывается строкой `<TAG арг1 арг2 …`, закрывается строкой `>`. Внутри — строки-атрибуты `ИМЯ значение …` и вложенные блоки. Токены разделяются пробелами; строки с пробелами заключаются в `"`, `'` или `` ` `` (выбор кавычки зависит от содержимого). Блоки состояния плагинов (`<VST`, `<AU`, `<JS`) и MIDI (`<SOURCE MIDI`) содержат многострочные данные (base64, события `E …`).

## Goals / Non-Goals

**Goals:**

- Побайтовый круг «файл → дерево → файл» для любого проекта корпуса.
- IR, покрывающий сущности из контрольного сценария: темп, размер, дорожки, элементы, тейки, цепочки FX, огибающие, маркеры.
- Локальная история с точным восстановлением и защитой несохранённой работы.
- Сравнение версий в терминах проекта.
- Одинаковое поведение на трёх ОС.

**Non-Goals:**

- Чанкинг аудио, ветки, слияние, сеть, фоновый агент, UI.
- Полное типизированное покрытие всех полей Reaper — непонятое сохраняется как есть.
- Разбор параметров внутри состояния плагина.

## Decisions

### D1. Дерево RPP хранит исходное представление токенов

Узел дерева: тег, список токенов, дочерние элементы (узлы и строки), причём каждая строка сохраняет исходный текст (отступ, кавычки, запись чисел, окончание строки). Писатель по умолчанию выводит исходный текст неизменённых строк и форматирует только изменённые.
**Причина:** побайтовый круг — простой и строгий критерий «ничего не потеряно»; иначе пришлось бы доказывать эквивалентность с точностью до форматирования чисел Reaper.
**Альтернатива:** нормализовать при записи и сравнивать семантически — отвергнуто, так как критерий размыт, а diff git по такому файлу шумит.

### D2. IR — проекция дерева с привязкой непонятого к владельцу

Адаптер Reaper обходит дерево и строит IR. Известные строки/блоки превращаются в типизированные поля; остальные складываются в `ext.reaper` сущности-владельца как упорядоченный список `{ключ, сырой текст}`, где ключ — имя атрибута или тега (с порядковым номером при повторах). Обратная сборка: писатель адаптера строит дерево из IR, вставляя `ext` на исходные позиции.
**Причина:** слияние (этап 3) сможет сливать непонятые поля «по ключу», не теряя их.
**Следствие:** порядок строк внутри блока при записи из IR — канонический для известных полей; побайтовый круг гарантируется для пути «файл → дерево → файл», а для пути «файл → IR → файл» гарантируется равенство IR (см. спецификацию `project-ir`).

### D3. Идентификаторы сущностей — GUID Reaper

`TRACKID` → Track.id, `IGUID` → Item.id, `GUID` тейка → Take.id, `FXID` → Fx.id, `EGUID` → Envelope.id. Если идентификатора нет (старые версии Reaper, огибающие без `EGUID`), он выводится детерминированно: хеш от ID владельца и роли (например, `env:<TrackId>:VOLENV2`). Дубликаты GUID в одном проекте — ошибка разбора с указанием сущностей.
**Открытый вопрос (проверить на корпусе):** поведение GUID при дублировании дорожки и «Save as».

### D4. Канонический JSON и хеширование

Объекты сериализуются в JSON с отсортированными ключами, без незначащих пробелов, UTF-8 NFC; числа с плавающей точкой — кратчайшая запись, однозначно восстанавливающая значение. Хеш объекта — BLAKE3-256 от байтов `"<тип> <длина>\0" + содержимое`, запись — hex. В каждом объекте поле версии формата.
**Альтернатива:** SHA-256 — медленнее на больших ассетах; protobuf — не читается глазами.

### D5. Раскладка `.soundgit/`

```
.soundgit/
  config            формат репозитория, путь к файлу проекта
  HEAD              ref: refs/heads/main
  refs/heads/main   хеш коммита
  objects/ab/cdef…  объекты (сжатие zstd для JSON-объектов; ассеты без сжатия)
  safety/           страховочные снимки: ссылки на коммиты вне истории ветки
  tmp/              временные файлы для атомарной записи
```

Запись объекта: во временный файл в `tmp/`, затем переименование. Обновление ссылки — так же. Один процесс-писатель одновременно: файл блокировки `.soundgit/lock`.

### D6. Ассеты на этапе 1 — целый файл как один объект

Объект `asset` уже имеет форму манифеста (`size`, `chunks: [hash]`), но содержит ровно один чанк — весь файл. Этап 2 заменит разбиение, не меняя формат снимка.
**Причина:** не переписывать снимки и восстановление при добавлении FastCDC.

### D7. Что считается ассетом

Файлы, на которые ссылаются `<SOURCE WAVE|MP3|FLAC|VORBIS|…>` c `FILE`, и которые лежат внутри каталога проекта. Ссылка вне каталога проекта на этапе 1 фиксируется как внешняя (путь + хеш + размер) с предупреждением; сбор в `media/` — этап 2. Отсутствующий файл — предупреждение, фиксация не прерывается (в снимке помечается `missing`).
Пик-файлы (`.reapeaks`), резервные копии (`.rpp-bak`), автосохранения — игнорируются.

### D8. Восстановление и страховочный снимок

`restore <версия>`: если рабочее состояние (файл проекта или ассеты) отличается от `HEAD`, сначала создаётся страховочный коммит в `safety/` и его идентификатор печатается. Затем `.rpp` и ассеты записываются атомарно; ассеты, совпадающие по хешу, не трогаются. `restore` не двигает ветку — рабочий каталог становится «изменённым относительно HEAD», и откат фиксируется обычным `commit` (история не переписывается).
**Альтернатива:** `restore` сам создаёт коммит-откат — отвергнуто: пользователь должен сначала открыть проект в DAW и убедиться, что это нужная версия.

### D9. Сравнение — структурное, с человекочитаемым выводом

Diff двух IR — список изменений `{вид: added|removed|modified|moved, путь сущности, поле, было, стало}`. Вывод CLI — текст по сущностям; флаг `--json` отдаёт тот же список для интерфейса и трека R4. Точки огибающих и MIDI-события сравниваются как последовательности, отчёт — «изменено N точек в интервале t1–t2».

### D10. CLI

Библиотека разбора аргументов — стандартная или минимальная зависимость; коды возврата: 0 — успех, 1 — ошибка, 2 — неверные аргументы. Все команды принимают `-C <каталог>`. Сообщения — на английском (ключи для будущей локализации в клиенте), `--json` у `status`, `log`, `diff`.

### D11. Версия хранит и модель, и исходный файл проекта [решение при реализации]

Снимок содержит IR (для сравнения и будущего слияния) и объект с байтами файла проекта, как он был на диске. `restore` записывает именно эти байты.
**Причина:** требование «файл проекта побайтово совпадает с зафиксированным» выполняется независимо от полноты адаптера; ошибка в адаптере не может испортить восстановление. Цена — файл проекта хранится дважды (сжатым).
**Альтернатива:** восстанавливать записью IR — отвергнуто для этапа 1: запись из IR побайтова только для файлов с каноническими отступами. С этапа 3 результат слияния будет записываться из IR — другого источника у него нет.

### D12. Раскладка сущности вместо «дерева с патчами» [уточнение D2]

Каждая сущность IR хранит `ext.layout` — список своих строк и вложенных блоков в исходном порядке: непонятые — как текст, понятые — с исходным текстом строки, позиции дочерних сущностей — метками. Писатель воспроизводит раскладку и заменяет в понятой строке только те значения, которые в модели читаются иначе. Дочерние сущности одного вида выводятся вместе на месте первой из них, в порядке модели.
**Следствие:** на синтетическом корпусе путь «файл → IR → файл» тоже побайтовый; сущность самодостаточна и переносится между версиями вместе со всеми своими данными (нужно для слияния).

### D13. Состояние редактора не является изменением [решение при реализации]

Курсор, масштаб, выделение, положение окон (список — в `MAPPING.md`) сохраняются в версии, но не показываются в `status`/`diff` и сами по себе не создают новую версию. Заголовок проекта с отметкой времени сохранения не сравнивается.
**Причина:** иначе каждое сохранение в Reaper выглядело бы изменением, а на этапе 3 давало бы ложные конфликты.
**Следствие:** `commit` после одного лишь перемещения курсора отвечает «нет изменений»; `restore` при этом всё равно делает страховочную версию, потому что байты файла отличаются.

### D14. Контрольная сумма файла отдельно от объекта хранения

У ассета в снимке два идентификатора: `hash` — BLAKE3 содержимого файла (не зависит от способа хранения) и `manifest` — объект со списком чанков. Этап 2 меняет только разбиение на чанки; сравнение версий и кэш по `hash` остаются.
Кэш контрольных сумм `.soundgit/index` (размер + время изменения → сумма) избавляет от перечитывания аудио при каждой команде.

## Risks / Trade-offs

- **Неизвестные конструкции `.rpp`** (редкие блоки, расширения SWS) → дерево обобщённое и не знает о семантике тегов; корпус пополняется реальными проектами; fuzz-тест круга.
- **Побайтовый круг ломается на окончаниях строк/BOM** → сохранять исходные окончания построчно; тест на CRLF-файле.
- **GUID окажутся неустойчивыми** → исследование на корпусе в первой группе задач; запасной вариант — сопоставление по (имя, позиция) как эвристика на этапе 3.
- **Большие проекты (сотни дорожек, длинные состояния плагинов)** → состояние плагина выносится в отдельный объект `blob`; бенчмарк разбора в тестах.
- **Числа с плавающей точкой дают ложные отличия** → IR хранит исходную текстовую запись числа рядом со значением; сравнение — по значению, запись — исходным текстом.

## Проверка на Reaper 7.86 (2026-11-15)

Корпус `testdata/rpp/minimal/` создан самим Reaper скриптом `tools/reaper/make-corpus.lua`. Адаптер, написанный по синтетическим файлам, прошёл на нём без правок: побайтовый круг и для дерева, и для пути «файл → IR → файл».

**Идентификаторы (ответ на вопрос D3):**

| Действие в Reaper | Что происходит с идентификаторами |
|---|---|
| Переименование, перемещение дорожки | Сохраняются |
| «Save as», повторное сохранение | Сохраняются; сохранение без правок даёт побайтово тот же файл |
| Дубликат дорожки | Новые `TRACKID`, `FXID`, `EGUID` — совпадений с оригиналом нет |
| Дубликат элемента | Новые `IGUID` и `GUID` тейков |
| Вставка дорожки в другой проект | `TRACKID` и `FXID` **сохраняются**, `EGUID` огибающих — новые |

Вывод: слияние по идентификаторам дорожек, элементов, тейков и эффектов обосновано. Для огибающих надёжнее ключ «владелец + цель» (у дорожки одна огибающая громкости), чем `EGUID` — решить на этапе 3.

**Что Reaper меняет сам — важно для этапа 3:**

- **Смена темпа сдвигает всё, что привязано к долям.** После `120 → 128` у каждого элемента изменились позиция, длина, фейды и скорость воспроизведения, у огибающих — время точек: в файле они в секундах. Слияние в секундах дало бы конфликт смены темпа с любой правкой аранжировки; позиции нужно сравнивать в долях (или пересчитывать через темп-карту).
- **Создание огибающей громкости переносит в неё значение фейдера**: громкость дорожки сбрасывается в 1.
- **Открытие и сохранение проекта добавляет строки** (`LANEREC` у каждой дорожки) **и пересохраняет состояние VST** — сравнение покажет «настройки плагина изменены», хотя пользователь ничего не трогал. Это источник ложных изменений и будущих ложных конфликтов; нужен способ сравнивать состояние плагина по смыслу или признать такие правки шумом.
- «Сохранить копию» (в отличие от «Save as») записывает абсолютные пути к медиа.
- Reaper пишет `.rpp` с окончаниями строк CRLF и на macOS. Тестовые данные поэтому исключены из преобразования окончаний строк в `.gitattributes` — иначе на Windows эталонные файлы и корпус расходятся с тем, что сравнивают тесты.

**Запись из модели:** файл, записанный из изменённой модели (имя с кавычками, микшер, порядок дорожек и эффектов, посылы, точки огибающей, элемент, тейки, маркер), Reaper открывает и читает с теми же значениями — тест `TestWrittenFileSurvivesReaper`.
